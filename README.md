# RedGuoAPI

RedGuoAPI 用于集中管理、同步和分发 JavaScript 模块，并提供模块索引与版本下载信息。

仓库将模块分为 **精简** 和 **全量** 两套目录与索引。两套数据相互独立；同一个模块可以同时存在于两套目录中。

## 目录结构

```text
RedGuoAPI/
├── modules/                 # 精简模块目录
│   └── <模块ID>/
│       ├── manifest.json
│       ├── main.js
│       └── UPSTREAM.json
├── moudules-all/            # 全量模块目录（目录名按现有约定保留）
│   └── <模块ID>/
│       ├── manifest.json
│       ├── main.js
│       └── UPSTREAM.json
├── index.json               # 精简模块索引
├── allindex.json            # 全量模块索引
├── new-modules.json         # 新模块登记及人工核查状态
└── sync-log.json            # 上游同步记录
```

> 注意：全量目录当前名称是 `moudules-all`，不是 `modules-all`。这是仓库现有目录约定，工作流和索引均按此路径读取，请勿自行改名。

## 精简与全量

| 类型 | 模块目录 | 索引文件 | 用途 |
| --- | --- | --- | --- |
| 精简 | `modules/<模块ID>/` | `index.json` | 提供精简模块列表 |
| 全量 | `moudules-all/<模块ID>/` | `allindex.json` | 提供完整模块列表 |

- 两套索引分别维护，不要把全量目录写入精简索引，也不要把精简目录写入全量索引。
- 同一个模块允许同时出现在两套目录中，两个目录中的文件分别维护。
- 上游同步发现模块同时存在于两套目录时，会分别检查并更新两份，不会只更新其中一份。
- 新发现的模块默认进入全量目录，并登记到 `new-modules.json`，等待人工核查。
- 人工核查通过后，使用“核查模块并复制到精简目录”工作流，将模块**复制**到 `modules/<模块ID>/`，同时更新 `index.json`。原全量模块及其索引记录会保留。

## 模块文件

每个模块目录至少包含：

- `manifest.json`：模块 ID、名称、版本、运行环境、API 版本、站点域名及能力声明等元数据。
- `main.js`：模块 JavaScript 主程序。
- `UPSTREAM.json`：上游仓库、分支、源码提交和文件摘要等来源信息。

模块 ID 应与 `manifest.json` 中的 `id` 一致，并与索引条目的 `id`、目录名一致。模块运行环境为 JavaScript，当前索引 API 版本为 1。

## 索引说明

### `index.json`

精简模块索引。模块条目的 `path` 应指向：

```text
modules/<模块ID>
```

### `allindex.json`

全量模块索引。模块条目的 `path` 应指向：

```text
moudules-all/<模块ID>
```

索引条目还包含模块版本、上游地址、发布标签、SHA-256 摘要及下载附件地址等信息。发布信息由工作流维护，手动编辑时应确保目录、版本、摘要和下载地址彼此一致。

## 自动化工作流

| 工作流 | 作用 | 触发方式 |
| --- | --- | --- |
| 上游模块自动同步 | 定期扫描上游模块仓库，检测源码及清单变化，并同步模块文件、索引和同步记录 | 每 2 小时自动运行，也可手动运行 |
| 模块自动发布 | 检查全量模块是否有新版本，生成 ZIP 发布附件并更新全量索引中的发布信息 | 上游同步成功后、全量目录或索引变更时，也可手动运行 |
| 核查模块并复制到精简目录 | 将指定模块复制到精简目录，保留全量原件，并更新对应索引和核查记录 | 手动运行，填写模块 ID |
| 校验模块目录 | 检查两套目录、索引、模块清单及新模块登记记录是否一致 | 相关文件变更时自动运行，也可手动运行 |
| 清理工作流运行记录 | 按选择清理已完成的 Actions 运行记录 | 手动运行 |

### 上游同步规则

1. 定时扫描上游组织中的模块仓库，读取默认分支上的 `manifest.json`、`main.js` 和最新提交信息。
2. 根据模块 ID 检查本仓库的精简目录和全量目录。
3. 已存在于某一套目录的模块，更新对应目录；两套目录都存在时，两套都会更新。
4. 新模块默认放入全量目录，并写入待核查登记。
5. 更新 `UPSTREAM.json`、对应索引和 `sync-log.json`，有实际文件变化时再提交仓库。

同步依据是上游默认分支的文件和提交变化，不要求上游必须先创建 Release 或 Tag。定时任务按两小时间隔发起，但 GitHub Actions 的实际启动时间可能有延迟。

## 发布规则

- 发布工作流以全量目录 `moudules-all/` 和 `allindex.json` 为发布来源。
- 模块版本从 `manifest.json` 的 `version` 读取，格式为 `主版本.次版本.修订版本`，例如 `1.2.3`。
- 发布标签格式为 `<模块ID>-v<版本号>`。
- 发布 ZIP 包包含 `manifest.json` 和 `main.js`。
- 发布成功或修复已有发布信息后，工作流会更新 `allindex.json` 中的标签、SHA-256 和下载地址。
- 源码有变化但模块版本号没有提升时，不会用同一个版本标签重复发布；应先在上游提升版本号。

## 日常维护注意事项

1. 新增模块时，目录名、清单中的 `id`、索引中的 `id` 必须一致。
2. 修改模块源码后，应同步更新模块版本号，再由发布工作流生成对应版本。
3. 不要手动混用两套目录和索引；精简目录对应 `index.json`，全量目录对应 `allindex.json`。
4. 不要删除全量原件来完成核查通过操作；核查流程是复制，不是迁移。
5. 不要修改 `moudules-all` 的拼写，除非同时调整所有工作流、索引路径和相关读取逻辑。
6. 如果同步工作流显示成功但模块没有更新，应进一步查看 Actions 日志及 `sync-log.json` 中的执行记录。

---

本仓库的核心原则：**上游负责提供模块源码，RedGuoAPI 负责同步、分类管理、校验、生成索引和发布；精简与全量两套数据各自独立维护。**
